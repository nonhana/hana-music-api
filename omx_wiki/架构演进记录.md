# 架构演进记录

- **状态**：archived reference
- **原始来源**：`stash/architecture.md`、`stash/PLAN.md` 与当前代码结构

## 演进主线

项目架构的演进可以概括为四步：

1. **迁移目标定型**：从旧 `netease-music-api` 引出 Bun + TypeScript + Hono 的新仓库结构。
2. **主链路打通**：完成 `crypto -> request -> server -> modules` 的服务闭环。
3. **接口与验证收口**：建立程序化 API、模块契约与 Phase 5/6 测试基线。
4. **交付面整理**：补齐 docs、`/demo/*`、PM2、README 与部署入口。

## 目录职责是如何稳定下来的

当前目录职责并不是一次性设计完成的，而是在迁移过程中逐步固定：

- `index.ts`：公共门面，负责导出服务启动、程序化 API 与公共类型。
- `src/app`：CLI、启动流程与匿名 token 初始化。
- `src/server`：Hono 服务组装、docs/demo 路由、模块装载与请求适配。
- `src/core`：请求、加密、缓存、运行时状态、通用工具。
- `src/modules`：与旧 `module/*.js` 对应的一文件一能力接口层。
- `src/plugins`：上传类等辅助能力。
- `src/demo`：本地调试 UI 子系统。
- `src/types`：运行时、请求、契约与上游边界类型。

## 几个关键架构决策如何落地

### 1. HTTP 与程序化调用共用模块注册表

无论是 `createServer()` 还是 `createModuleApi()` / `invokeModule()`，底层都依赖 `loadModuleDefinitions()` 装载模块定义。这让 HTTP 服务与 SDK 式调用共用同一组业务模块，而不是两套重复实现。

### 2. 请求兼容逻辑集中在 `src/core/request.ts`

项目没有把 Cookie、IP、加密模式、Header 拼装等兼容逻辑散落到每个模块，而是集中在 `createRequest()` 中处理。这也是为什么很多迁移模块只负责“组装上游 data + 调用 request”。

### 3. Demo UI 与文档站分离

`/docs` 负责对外说明与 API 参考，`/demo/*` 负责本地调试体验。二者复用同一进程，但职责分离，避免把 VitePress 当调试壳层，也避免为 Demo 再引入一套前端工程。

### 4. 历史兼容靠测试与包装层维持

批量迁移模块并没有在第一轮全部做到深度类型化，而是借助：

- `_migration.ts` 的兼容包装
- Phase 5 回归测试
- 服务层与程序化 API 测试

共同守住旧行为契约。

## 当前架构判断

截至当前代码状态，项目架构已经不是“迁移草图”，而是**稳定的服务应用结构**。后续更适合围绕：

- 发布闭环
- 质量收口
- 长尾类型优化

做增量维护，而不是重新设计主架构。
