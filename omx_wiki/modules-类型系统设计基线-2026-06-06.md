# Modules 类型系统设计基线（2026-06-06）

## 背景与问题定义

本页是 `src/modules` 类型系统的后续规划基线，不是直接实施方案。

当前仓库已经完成运行时模块迁移，但模块类型系统仍然分裂成三套事实源：

1. 运行时模块注册表来自 `src/modules` 文件系统扫描。
2. API 文档来自当前公开模块 surface 的生成结果。
3. TypeScript SDK 的静态精确类型来自 `ModuleContractMap` 里的手工白名单。

这导致当前问题不应再表述为“继续补完剩余 300 个模块类型”，而应表述为：

- 运行时可发现性已经接近全量。
- 文档可见性已经接近全量。
- SDK 精确 typing 仍被 64 条手工契约卡住。
- `src/types/modules.ts` 与 `src/types/module-contracts.ts` 正在同时承担“模块全集 + shared shape + 精确 override”三种职责。

## 当前系统事实

### 结构事实

- `src/server/module-loader.ts:16-37`：`loadModuleDefinitions()` 直接扫描 `src/modules`，生成 `identifier` 与 `route`。
- `src/server/create-server.ts:18-40`：HTTP 服务把这份模块定义注册到 Hono。
- `src/app/module-api.ts:44-124`：程序化 API 也复用同一份 registry，但静态签名来自 `ModuleContractMap`。
- `src/types/module-contracts.ts:58-142`：`ModuleIdentifier = keyof ModuleContractMap`，`ProgrammaticApi` 也是从该 map 派生。
- `docs/api/index.md:1-35` 与 `docs/.vitepress/config.ts:1-33`：公开 API 文档是生成式 surface，而不是手写逐页维护。
- `tests/module-api.test.ts:135-415`：程序化 API 的 typed module identifiers 只锁定了部分高价值模块。
- `tests/phase-5-regression.test.ts:13-220`：兼容回归测试优先锁行为，不是锁 300+ 长尾模块的精确输入类型。

### 复杂度事实

对 `300` 个 `LegacyModuleQuery` 模块做静态复核后，distinct `query.xxx` 读取分布仍然呈现明显长尾：

| Distinct query fields | Module count |
| --------------------- | ------------ |

| `1`                   | `93`         |

这说明多数长尾模块更像“shared shape 组合 + fallback typing”问题，而不是 300 个完全独立的 bespoke interface 问题。

## 设计目标

1. 让 TypeScript 能静态看见 runtime 能加载的全部模块，而不是只看见 `ModuleContractMap` 白名单。
2. 把 query/input typing 作为第一优先级，先修正输入层架构，再考虑 response 精细化。
3. 让 shared query shapes 成为默认建模单位，只有高价值模块才拥有 curated override。
4. 允许不同模块停留在不同 precision tier，不再假装每个模块都必须等精度。
5. 保留现有回归测试对 legacy 行为的约束，不把类型改造变成行为改写。

## 非目标

1. 不再继续把剩余 300 个模块机械追加到 `src/types/modules.ts`。
2. 不让 `ModuleContractMap` 同时承担“模块全集”与“精确 override 集”两种职责。
3. 不以“全量 366 个模块都手工建精确 query 类型”作为阶段目标。
4. 不在 query/input 架构未整理前优先追求 response exactness。

## 模块分层模型

### Layer A: generated all-module surface

这一层只解决“模块可见性”。

- 数据来源：`loadModuleDefinitions()` 的真实扫描结果，或与其等价的构建期文件扫描。
- 产物目标：全量 `ModuleIdentifier`、模块路由、基础 `ModuleQuery` fallback、保守 `NcmApiResponse` fallback。
- 关键约束：SDK discoverability 不能依赖某模块是否已经有人工 override。

### Layer B: shared query primitives and reusable shapes

这一层只解决“重复输入结构复用”。

- 基础 primitives 继续保留：`QueryIdentifier`、`QueryNumberLike`、`QueryBooleanLike`、`OptionCompatibleQuery`。
- 设计原则：优先组合 shared shapes，再决定某模块是否值得单独 override。
- 判断口径：是否跨多个模块复用、是否与长尾字段分布一致、是否能直接降低手工维护面。

### Layer C: curated typed overrides

这一层只解决“高价值模块的人体工学 typing”。

- 只收录确实值得精确签名的模块。
- 允许数量远小于模块全集。
- 与 Layer A 分离后，未进入 override 集的模块仍然要对 SDK 可见，只是 query 使用 fallback 或 shared 组合。

## Typed Override 准入标准

模块只有在同时满足“shared shape 组合仍不足够表达 DX 价值”时，才应该进入 curated override 集。建议准入标准如下：

1. 该模块很可能被 SDK 用户直接调用，而不是只经 HTTP 透传。
2. query contract 存在明显分支、互斥关系、默认行为或容易误用的参数。
3. 模块涉及登录、注册、上传、写操作、账号变更或其它高风险行为。
4. 模块已经有稳定测试或文档证据支撑其输入语义。
5. 模块足够典型，适合作为某一类能力的 DX exemplar。

建议的反向筛除规则：

1. 如果 query 只比某个 shared shape 多一个薄别名，不应保留独立 override。
2. 如果 query 基本为空对象或只有 transport 选项，不应仅为了“名字好看”保留精确 override。
3. 如果模块仍处于长尾兼容态、缺少测试/文档证据，应优先停留在 shared shape + fallback。

## 推荐的后续 Plan 边界

后续正式 plan 建议只覆盖下列边界，不要在同一轮里扩散成“全面重构”：

1. 建出 Layer A 的 generated all-module surface，并让静态 `ModuleIdentifier` 不再只来自 `ModuleContractMap`。
2. 把 `src/types/modules.ts` 拆成 primitives/shared shapes 与 endpoint overrides 两层。
3. 先迁移上表中的 “keep shared” 与 “merge” 两类，再保留 “endpoint override” 的最小精确集。
4. 继续依赖 `tests/module-api.test.ts`、`tests/phase-5-regression.test.ts`、`tests/audio-match.test.ts`、`tests/voice-upload.test.ts` 作为行为护栏。
5. 本轮不处理 response exactness，也不要求 300 个 legacy 模块同步提升到同一精度。

## Operational Note

如果下一线程继续从这个基线推进，应保持工具输出保守：

1. 优先做计数、top-N 与聚合表，不再做大面积 `rg` 原始输出。
2. 避免同时扫描 `.` 与子目录，减少重复流量。
3. 研究阶段优先回答“这个 shape 是否值得共享 / override”，而不是再次回到“是不是把剩余模块继续补进 `ModuleContractMap`”。
