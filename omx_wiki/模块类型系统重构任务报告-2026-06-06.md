# 模块类型系统重构任务报告（2026-06-06）

## 1. 任务背景

本轮任务的直接背景，是 `hana-music-api` 在完成 `src/modules` 运行时迁移之后，类型系统出现了结构性错位：

1. 运行时模块发现已经基本以 `src/modules` 文件系统扫描为准。
2. 文档公开面已经基本覆盖当前公开模块。
3. TypeScript SDK 的静态精确类型仍然主要依赖手工维护的 `ModuleContractMap` 白名单。

这个错位带来的核心问题不是“还有 300 多个模块没补类型”，而是：

- **模块可发现性** 和 **类型精度** 被耦合在一起。
- 一个模块如果没被写进手工白名单，就会在 SDK 静态面里“看不见”。
- `src/types/modules.ts` 与 `src/types/module-contracts.ts` 同时承担了模块全集、shared shape 和 endpoint override 三类职责。

在此基础上，上一个线程先沉淀了交接文档和设计基线，本轮任务的目标不再是继续讨论方向，而是：

1. 在已确认基线的前提下完成可执行 planning。
2. 把 planning 通过 `ralplan -> ultragoal` 落成可审计的执行链。
3. 真正完成模块类型系统的重构实现、验证和最终 gate。

## 2. 分析过程与上下文明确历程

### 2.1 初始交接分析

本轮开始时，先读取了交接文档：

- `.omx/notes/2026-06-06-modules-type-system-handoff.md`

通过交接文档和代码现状复核，确认了以下关键事实：

1. 运行时模块发现来自 `src/server/module-loader.ts`，并且本质上是文件系统驱动。
2. HTTP 服务和程序化 API 共享同一份模块注册表来源。
3. 静态 SDK 类型面由 `src/types/module-contracts.ts` 决定，而不是由运行时真实模块集合决定。
4. 文档站公开面和 SDK 精确类型面并不一致。

这一步的结论是：当前问题必须按**架构重构**来处理，而不是按“补更多接口类型”来处理。

### 2.2 基线确认

在交接基础上，本轮继续补齐了一份新的 wiki 基线：

- `omx_wiki/modules-类型系统设计基线-2026-06-06.md`

这份基线明确了三层模型：

1. **Layer A**：generated all-module surface
2. **Layer B**：shared query shapes
3. **Layer C**：curated typed overrides

同时，也明确了对旧 `64` 条强类型条目的迁移规则：

- 哪些保留为 shared shape
- 哪些保留为 endpoint override
- 哪些并入其它 shared shape
- 哪些降级回 compatibility fallback

### 2.3 规划阶段

在方向明确之后，没有直接开改代码，而是走了完整的 OMX 规划链：

1. 使用 `$ralplan` 生成 PRD 和 test spec
2. 顺序通过 `architect -> critic` 共识门
3. 在规划中明确：
   - phase 1 必须保留 `src/types/modules.ts` 作为 compatibility facade
   - generated surface 必须进入正式验证链路
   - public entry type exports 必须有 compile-only fixture 锁住

规划产物落在：

- `.omx/context/module-type-system-refactor-20260605T165942Z.md`
- `.omx/plans/prd-module-type-system-refactor-20260605T165942Z.md`
- `.omx/plans/test-spec-module-type-system-refactor-20260605T165942Z.md`

### 2.4 执行阶段

在规划完成后，切换到 `$ultragoal`，把任务拆成 4 个 durable stories：

1. 建立 shared discovery 和 generated module surface
2. 拆分 canonical shared shapes 并重组 public contracts
3. 升级 module API typing 与验证面
4. 更新文档并完成最终 verification / review gate

这一步的关键不是“一口气大改所有文件”，而是每个 story 都单独 checkpoint，并且只有在：

- 目标完成
- 测试通过
- 证据完整

之后才写入 ultragoal ledger。

## 3. 代码层面的落地计划

本轮在代码层面的实际落地，遵循了下面这条主线：

### 3.1 Discovery 单一事实源

先把模块发现逻辑从 `module-loader` 中抽出来，做成可以同时服务：

1. runtime loader
2. generated type surface
3. parity test

的共享入口。

目标是避免：

- 运行时发现一套规则
- 生成器再复制一套规则

从而降低 drift 风险。

### 3.2 先建立 generated fallback universe

在不破坏现有模块行为的前提下，先建立一个全量的 generated module type surface：

- 所有 runtime-known modules 都进入静态面
- 但默认 query / response 先退回 compatibility fallback

这一步先解决“看得见”，不强行提前解决“每个都精确”。

### 3.3 再拆 shared / override 层

在有了全量 generated surface 之后，再把原来混在 `src/types/modules.ts` 里的类型分层：

1. shared primitives / shapes
2. endpoint-specific overrides
3. `modules.ts` compatibility facade

这样可以让新架构成立，同时不逼着 `src/modules/*` 立即做 repo-wide import 迁移。

### 3.4 最后重组 public contract surface

等 generated universe 和 shared / override 分层都成立之后，再重组：

- `ModuleContractMap`
- `ModuleIdentifier`
- `ModuleQueryOf`
- `ModuleResponseOf`
- `ProgrammaticApi`

并通过 compile-only fixtures 证明 public entry surface 真正稳定。

### 3.5 把 generator 纳入正式验证链路

如果 generator 只是“可选工具”，那 drift 风险仍然存在。

所以最终把：

- `types:modules:generate`

纳入了：

- `verify`

的执行链路，并补了 generated/runtime parity test。

## 4. 具体改了哪些文件，怎么改的

### 4.1 运行时 / discovery 相关

#### `src/server/module-discovery.ts`

新增文件，承接模块发现和路由推导逻辑。

主要职责：

1. 扫描 `src/modules`
2. 生成 `identifier`
3. 生成 `route`
4. 统一特殊路由映射

这让 runtime loader 和 generator 都能使用同一套 discovery 规则。

#### `src/server/module-loader.ts`

从“自己扫描并推导模块”改为“消费 shared discovery helper”。

这样 loader 本身只保留：

- import 模块
- 校验 default export
- 返回 `ModuleDefinition[]`

而 discovery 规则不再散落在这里。

### 4.2 generated type surface 相关

#### `scripts/generate-module-type-surface.ts`

新增生成脚本。

主要行为：

1. 读取 shared discovery 结果
2. 生成 `generatedModuleIdentifiers`
3. 生成 `generatedModuleRoutes`
4. 生成 `GeneratedModuleContractMap`
5. 自动格式化生成文件

#### `src/types/generated/module-surface.generated.ts`

新增 committed generated artifact。

这个文件提供：

1. 全量 runtime-known module identifiers
2. identifier -> route 映射
3. 默认 fallback contract universe

这一步让“模块可发现性”不再依赖手工白名单。

### 4.3 类型分层相关

#### `src/types/module-shared.ts`

新增 canonical shared layer。

主要收纳：

- `LegacyModuleQuery`
- `OptionCompatibleQuery`
- `QueryIdentifier`
- `QueryNumberLike`
- `QueryBooleanLike`
- `AlbumQuery`
- `ArtistQuery`
- `CommentThreadQuery`
- `UserScopedListQuery`

等高复用 shared shapes。

#### `src/types/module-overrides.ts`

新增 endpoint-specific override layer。

主要收纳：

- `SearchQuery`
- `LoginQuery`
- `LoginCellphoneQuery`
- `SongUrlQuery`
- `SongUrlV1Query`
- `VoiceUploadQuery`
- `CloudQuery`
- `BatchQuery`

等不适合只靠 shared shape 表达的精确契约。

#### `src/types/modules.ts`

从“所有东西都写在这里”改成：

- **compatibility facade**

也就是只做：

1. re-export `module-shared.ts`
2. re-export `module-overrides.ts`

这保证了已有 `src/modules/*` 的 import 面不需要在 phase 1 做大规模迁移。

### 4.4 public contract 重组相关

#### `src/types/module-contracts.ts`

这是本轮最关键的 public type surface 重组点。

主要变化：

1. 保留 `ModuleOverrideContractMap`
2. 新增：
   - `ModuleContractMap = Omit<GeneratedModuleContractMap, keyof ModuleOverrideContractMap> & ModuleOverrideContractMap`
3. 继续导出：
   - `ModuleIdentifier`
   - `ModuleQueryOf`
   - `ModuleResponseOf`
   - `ProgrammaticApi`
4. 新增 override-key parity guard，确保 override key 不能漂出 generated identifier set

这一步的意义是：

- 全量 discoverability 进入 static surface
- promoted modules 仍保持精确 typing
- fallback modules 进入可见但保守的 contract 层

#### `package.json`

新增：

- `types:modules:generate`

并把它纳入：

- `verify`

这让 generator 不再是“记得跑就跑”的工具，而是正式质量门的一部分。

### 4.5 测试与验证相关

#### `tests/module-discovery-alignment.test.ts`

新增 runtime/generated parity test。

作用是：

- 比较 live discovery
- 比较 generated identifiers / routes

确保 generated surface 不会静默漂移。

#### `tests/module-api.test.ts`

补了一条真实 fallback module 的 runtime test。

作用是证明：

- fallback module 不只是编译时“看得见”
- runtime 调用也真的能通过统一 API surface 正常工作

#### `tests/module-api.typecheck.ts`

新增 promoted-module compile-only fixture。

用于锁：

- `search`
- `comment_music`
- `song_url`
- `login_cellphone`
- `voice_upload`

等高价值模块的精确类型行为。

#### `tests/public-entry.typecheck.ts`

新增 public entry compile-only fixture。

这份测试最终承担了非常关键的 public contract 证明：

1. `ModuleIdentifier`
2. `ModuleQueryOf`
3. `ModuleResponseOf`
4. `ModuleContractMap`
5. `ProgrammaticApi`

都能通过 `../index.ts` 被正确消费。

同时，它也证明：

- fallback module `top_song` 可以从 public entry 调用
- 返回类型保持保守 `NcmApiResponse`
- unknown identifier 在编译期报错

### 4.6 文档相关

#### `docs/guide/programmatic-api.md`

更新为新的用户心智模型：

1. **模块可发现性**
2. **类型精度**

文档明确解释：

- 所有 runtime-known modules 都能被静态发现
- 只有部分高价值模块有更强 query typing
- 长尾模块虽然可见，但仍然停留在 compatibility fallback

#### `omx_wiki/modules-类型系统设计基线-2026-06-06.md`

这是本轮前半段沉淀下来的设计基线页，为后续 planning 和 execution 提供了稳定约束。

#### `omx_wiki/index.md`

更新 wiki 索引，把基线页纳入可发现面。

## 5. 踩坑历程

本轮有几个比较典型的坑：

### 5.1 不能直接把完整 PRD 当 ultragoal brief 原样喂进去

第一次直接用完整 PRD 做 `ultragoal create-goals` 时，goals 被拆得过细，甚至把标题、条目和普通句子都当成了单独 goal。

后来改成：

- 手工指定 4 条 story 级目标

才让 ultragoal 的执行粒度回到可控范围。

### 5.2 public-entry fixture 一开始不够强

第一次 final review 时，`code-reviewer` 指出：

1. `tests/public-entry.typecheck.ts` 没有真正锁 public type exports
2. fallback module 的 compile-only 证明也不够强

这一步逼着测试从“能调用”升级成：

- 明确引用 `ModuleIdentifier` / `ModuleQueryOf` / `ModuleResponseOf` / `ModuleContractMap` / `ProgrammaticApi`
- 明确断言 fallback 返回类型是 `NcmApiResponse`

这个补强非常关键，否则 public SDK 风险没有真正锁死。

### 5.3 architect 最终卡的不是核心架构，而是 seam hardening

第一次 architect final review 不是 `BLOCK`，但给了 `WATCH`。

问题集中在：

1. manual override layer 是否有 parity guard
2. generator 是否进入正式 `verify`

后来通过：

- `InvalidModuleOverrideKeys`
- `verify` 先跑 `types:modules:generate`

这两步把 seam 风险收口掉。

### 5.4 最后 `verify` 被历史格式问题卡住

在 final gate 快结束时，`verify` 只剩一个问题：

- `omx_wiki/log.md` 的既存格式不符合 `fmt:check`

这不是产品逻辑问题，但它会阻断真正的全绿质量门。

最终采取的处理方式是：

- 先把本轮 execution 触碰文件全部格式化
- 再把 `omx_wiki/log.md` 做纯格式归一化

从而拿到真正的 green `bun run verify`

## 6. 总结

本轮任务的成果，不是“补了一批接口类型”，而是把模块类型系统从原来的手工白名单模式，重构成了一个更接近现代 TypeScript SDK 实践的分层模型：

1. **运行时 discovery 单一事实源**
2. **generated fallback universe**
3. **shared query shapes**
4. **curated endpoint overrides**
5. **compatibility facade**
6. **public-entry compile-time contract verification**

具体来说，这次重构解决了三个关键问题：

1. 模块是否可见，不再依赖是否已手工写进白名单。
2. 长尾模块终于可以“可发现但不伪装精确”。
3. 高价值模块依然保留了强 query typing 和更好的 SDK DX。

从验证结果看，本轮最终已经完成了：

- `bun run verify` 全绿
- `code-reviewer = APPROVE`
- `architect = CLEAR`
- ultragoal 4 条 story 全部 checkpoint 完成

因此，这轮工作已经不是“方向正确但尚未收尾”，而是**一次完整完成、带有 planning 证据、执行证据、测试证据和 review 证据的架构重构闭环**。

后续若继续推进，更适合做的是：

1. 持续把高价值 long-tail modules 提升进 curated overrides
2. 把这套 generated + override 模式推广到更多 SDK surface
3. 在 CI / 发布流程里持续强化这套质量门

但这些都属于后续成熟化工作，而不影响本轮任务已经完整收口。
