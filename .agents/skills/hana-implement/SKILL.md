# 实施 hana-music-api 需求

路径以仓库根为准；本文件内的链接相对 skill 目录。先读 [AGENTS.md](../../../AGENTS.md) 与 [TESTING.md](../../../agent-docs/TESTING.md)，再按改动读取其余 agent-docs、领域文档与 ADR。TESTING 是门禁和完成判定的唯一权威，本 skill 调度执行，不另定一套标准。

## 1. 确定输入、范围与授权

按用户实际输入读取来源：

- ticket：通过 `gh issue view` 读取完整标题、正文与明确引用的父约束，声明本次处理的标题。旧路径以当前树核对后更新映射，保留来源。跟踪器操作见 `docs/agents/issue-tracker.md`。
- plan：完整读取指定文件，提取目标、非目标、切片依赖、Verification 与 Done when；按用户指定范围实施，历史调查数字先核对。
- 提示词：保留原要求和后续澄清，把可观察结果写成 AC；直接输入同样有效，无需先开 issue。

形成 goal / scope / non-goals / AC / seams / gates / source / authorization。最新明确用户要求控制当前范围；已确定的架构边界直接沿用，只有会改变结果的缺项或冲突才聚焦询问，并继续独立工作。计划请求只形成计划；进入实施必须来自用户本次指令。已有实施或提交授权直接承接，旧票与参考 skill 中的历史许可没有本次效力。

完成条件：来源完整，范围、必要条件和当前权限可判断，后续实现能逐条验收。仅计划请求到此形成 AC、切片依赖、Verification/Done when 与未来门禁后结束，不进入实施、生成、测试执行或交付动作。父合同中适用约束保留，其他切片的完成项不自动扩成本片范围；来源明确要求的额外门禁与 TESTING 合并登记。

## 2. 保护基线并建立需求矩阵

检查分支、HEAD、工作区和实际测试清单。固定起始 base，记录已有用户改动的文件、内容与归属；持续保留它们。按 [验收模板](../../../docs/acceptance/template.md) 保存 `docs/acceptance/<slug>.md`，结果保存 `docs/acceptance/runs/<slug>.md`。ticket 可用 issue-105，plan/prompt 用稳定主题名，不复制 skill 充当需求。记录规模服从实际任务；用户明确限制改动文件或指定演练输出位置时在其允许位置保存矩阵/结果，不扩大文件范围。

在实现前逐条列 AC、实际入口、期望结果、seam、已有/新增测试标题或独立证据、专项适用性及原因、缺失条件。按 TESTING 的变更性质选择 unit / behavior / replay / transport / package / live / mutation，检查当前 package.json 与 suites.ts 中的实际命令。

完成条件：每条 AC 有决定性证据目标，门禁没有在失败后被改为不适用；已有用户改动可与本任务区分。

## 3. 连续实施并验证行为

按切片依赖顺序完成实现、Verification 和 Done when，再进入下一切片，无需逐片请求继续。每个新行为先用最窄而真实的边界观察 red，再 green；已有有效回归直接复用并说明，不故意破坏产品制造 red。记录 red 的具体断言原因，导入/环境错误不能冒充行为 red。

从公开 SDK/HTTP 入口走真实模块和单执行链，在网络边界使用严格 fake；纯规则用 unit，原文响应用 replay，socket/包/live 按各自能证明的边界取证。针对改变的关键判定运行登记 mutation；缺少对应故障时补有限目标，不用无关目标的 killed 声称覆盖新判定。不机械新增七套测试。保留既有验证责任、公开 API、身份隔离、总期限/取消、写请求单次策略。共享 helper 遵守 CODE_STYLE 的实际消费者要求；生成物通过生成器更新。

旧计划描述与现状不符时先核验已有实现，缺项才实现，不为制造新 diff 重写已满足部分。纯文档任务按 TESTING 选择语义对照、diff 和文档门禁，裁剪代码 red/green、mutation、包与 live 等不适用步骤。

同时更新受影响文档、路径消费者、必要 changeset 与 ADR。每片记录实际命令、结果、候选指纹、日志路径和剩余项，便于跨上下文接续。

完成条件：该片每项行为和保留责任有证据，全部适用检查通过；外部阻塞单列，并继续不依赖它的工作。

## 4. 验证最终候选与外部条件

冻结内容后，按 TESTING 串行运行全部适用门禁，保存 `.artifacts/testing/` 的原始日志、JUnit、包/源码指纹及验收结论。修复、生成、版本变更或依赖变化后重新验证受影响检查，最后所有适用结果指向同一候选。

需要 live 时按 TESTING 的 gate、请求预算和当前授权执行；真实上游使用安装后的候选包。匿名只读也需当前任务授权。登录需要当前账号/期望身份，写入另需单个目标、fresh token、写入及恢复授权。缺条件写阻塞，不用 skip、假上游或历史报告替代，也不从旧票自动设置写 gate。无需 live 的任务说明不适用即可。真实写失败停止业务，恢复未确认单列失败。

完成条件：每项适用门禁有当前 PASS / FAIL / BLOCKED 证据，未运行与不适用按 TESTING 如实登记并说明原因，真实与替身结果分开，凭据没有进入仓库或日志。

## 5. 双轴审查、修复并交付

按 [review.md](references/review.md) 提供来源、基线、完整工作区证据包和真实日志。代码改动由未参与实现的独立 agent 或 reviewer 审查；审查者直接读代码与日志，分别核对仓库规范和需求验收。环境无法提供独立审查时记录该项阻塞，不假称已审查。

修复发现后重跑受影响验证，刷新候选并再次审查。实施审查的空 diff、缺来源或缺必要结果不能判通过；既有失败同样计入验收。若只核验已存在的实现，明确报告当次证据和“无新增实现”，不冒称交付新代码，也不制造改动或空提交。仅准备审查包时交付完整输入与缺项状态，不冒称已完成代码审查。只有 TESTING 的完成条件全部满足才能说完成，代码能力、外部专项、远端运行分别报告。

提交、推送、PR、关票、合并、账号写入与发布分别按本次授权执行。明确授权的动作不重复请求；未授权的外部动作保持待执行，先交付具体可审查工作区。审查本身不产生自动提交，尚未发布不等于已发布。

完成条件：每条 AC、检查、审查和授权内交付均有明确状态，余项写明具体缺失条件与下一动作。

维护者按 [input-cases.md](examples/input-cases.md) 组织隔离演练；独立执行者只接收现实请求、skill 与必要原始来源，先产出决策，再由维护者对照预期。用户指定的盲测方案和输出位置优先。不能用关键词存在代替行为演练。
