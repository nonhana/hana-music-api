# 歌单收藏 405 调查记录

截至 2026-10-17 深夜，稳定性验收仍未完成。接续调查已确认两类拒绝：自称 pc/iphone 但缺少客户端特征的请求会被单独拒绝；没有易盾一次性令牌的请求在连续操作后会进入按路径生效的数小时拒绝窗口，官方客户端因令牌不受影响。公开模块已改为官网的网页写法，但尚未在限制解除后取得重复性成功证据。本记录属于 [#77](https://github.com/nonhana/hana-music-api/issues/77) 的调查证据，不是可用性承诺。

**后续进展：**16:43–17:09 的[深入调查](./playlist-subscription-research.md)补齐了实际出站 Cookie、上游源码追溯和“成功 → 只增加 `os=iphone` 后失败 → 去掉后成功”的反向对照。已确认这个平台标记会在所测条件下触发拒绝，但它不足以解释全部失败：两个候选模块仍失败，之后已成功的官方原样请求重放也返回 405。第一个正式窗口完成 **0/3**，已停止；候选代码已撤回。23:00 的接续调查进一步确认：新会话、新目标上公开模块仍被拒，官方 Mac 客户端收藏会携带当场申请的一次性反作弊令牌，限制按路径而非整号计算。下文保留 16:05–16:13 的首阶段记录，数量和验收状态均不包含后续实验。

**10-18 修正：**后续实验用本地 Watchman 现取的 170 字符令牌让公开链路成功一次（无缓存列表 54 → 55，取消后恢复 54/36），但新的无头设备令牌连续 405；令牌必须来自稳定设备/会话。SDK 已支持 `checkToken` provider，见[接续记录](./playlist-subscription-research.md#check-token-continuation)。本文中“公开模块已改为官网网页写法”是 10-17 的阶段状态，不再作为最终方案。

## 环境与前置状态

- SDK：`hana-music-api@2.9.0` 源码 `7671080`；该提交和 `1c7ba77` 是接手时已有、尚未推送的 #33 证据提交，本次 PR 一并保留。
- 运行位置：同一台本机；官方网页由 Chromium 打开 `https://music.163.com`，通过真实界面发起操作。未测官方 Mac 或 iPhone 原生客户端。
- 会话：用户提供的已登录 Cookie 导入独立浏览器会话；核对网页与 SDK 的 `MUSIC_U`、`__csrf` 值相同。原始登录方式、登录设备未知，不能把本次标为扫码登录或原生客户端登录。
- 目标：他人公开歌单 `2889745179`。16:05:53 通过公开 SDK 的登录状态、无缓存歌单列表和详情确认会话有效、目标属于他人且未收藏。
- 基线：53 张歌单，35 张收藏。对全部歌单的 `id` 和 `subscribed` 排序后计算 SHA-256；每组之后核对完整快照，不只核对数量。私人歌单 ID、账号 ID 和凭据不写入本记录。
- SDK 探针关闭缓存和重试，逐个发送；列表单页上限 1,000，并要求 `more=false`。浏览器会自行加载页面资源和发送遥测，不能把浏览器总流量描述成只有两次请求。

官方网页取消操作需要进入「我的音乐」并确认移除，距收藏约 70 秒。这是诊断对照，不符合稳定性窗口要求的立即取消，不能计入验收轮次。

首次网页探针把所有导入 Cookie 都设成 HttpOnly，错误地阻止了官方脚本读取 `__csrf`。该请求的明文 `csrf_token` 为空，返回：

```json
{
  "code": 403,
  "message": "illegal request!",
  "debugInfo": null,
  "data": null,
  "failData": null,
  "msg": "illegal request!"
}
```

停止后仅将 `__csrf` 改为脚本可读，并确认后续请求含非空 CSRF；随后官网操作成功。这个 403 归因于探针配置，不能作为 SDK 405 的证据。

三次有效失败探针的 HTTP 状态均为 200，原始正文均为：

```json
{
  "code": 405,
  "message": "操作过于频繁，请稍后再试",
  "debugInfo": null,
  "data": null,
  "failData": null,
  "msg": "操作过于频繁，请稍后再试"
}
```

两次公开 SDK 调用都以 `status: 405` 拒绝，正文保留上述字段并补充 `retryAfter: 30`。这个 30 秒是 SDK 缺省值，不是上游提供的恢复时间。冻结请求探针直接观察原始 HTTP 返回，没有经过 SDK 响应映射，不应混称为公开模块成功或失败验证。

官方脚本的加密函数在不改变入参、返回值的前提下被观察，用于记录上述明文键。网页成功时加载的脚本为 `core_c7686f506f6f2607bb7f6cea1951f039.js`；其收藏定义将业务数据设为 `{ id }`，取消定义将 `pid` 赋给 `id`，协议层添加 CSRF 并转为 weapi POST。

抓取工具的 HAR 与请求详情没有包含浏览器实际发送的 Cookie 头。因此浏览器 Cookie 存储检查只能证明可用会话和字段集合，不能证明逐字节的出站 Cookie 与 SDK 相同。原始 HAR、带认证的冻结请求及账号快照只保存在本机，不能直接发布。

## 首阶段可以得出的结论

1. 同一会话在相近时间能通过官方网页完成收藏和取消；不能将本次 SDK 405 简化为“账号完全不能收藏”。两次操作之间存在时间和请求差异，也不能排除按客户端、设备或请求特征区分的上游风控。
2. **仅把公开 SDK 的 `crypto` 改成 weapi 不足以解决。** 该实验仍保留 SDK 的 iPhone 身份与其他请求处理；不能把失败扩展成“weapi 不可用”，因为官方网页的 weapi 已成功。
3. **只移除失败 weapi 请求的转发 IP 头也不足以解决。** 它复用已失败请求的加密正文，不是一次全新官网请求；结果不能排除请求时效、重复检测或其他字段共同作用，也不能证明 IP 永远无关。
4. 没有确认某个设备字段、UA、Cookie 或反作弊机制就是间歇性 405 的根因。当前证据不足以支持替换固定身份、自动降级协议、补入静态 token 或自动重试写操作。

## 首阶段结束时的验收状态
