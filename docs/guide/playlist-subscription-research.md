# 歌单收藏 405：请求身份与时序的深入调查

<!-- cspell:ignore APNIC RDAP DIGITALPACIFIC SGCABLEVISION Referer -->

2026-10-17 的调查确认了一个具体拒绝条件：**在本次成功的官方网页请求中，只增加 `os=iphone` Cookie 就会得到 405；去掉它，原样请求又成功。**这证明客户端身份标记可以触发相同的“操作过于频繁”正文。

但这还不是完整根因。`weapi + os=web` 的 SDK 探针曾成功，落到公开模块后却再次失败；稍后，先前成功的官方请求重放也被拒绝。当前证据同时包含请求字段差异和随时间变化的响应，不能把所有 405 归为同一个原因。**候选修复已撤回，#77 保持未解决，正式窗口 0/3。**

## 一手资料与实际请求

### NMTID 的处理确有差异，但不是现成答案

本地 [`processCookieObject`](https://github.com/nonhana/hana-music-api/blob/c832da277cdfce9bcf0a4876f01d5f3be1aabe5b/src/core/request-plan.ts#L176) 在非登录请求中无条件把 `NMTID` 换成随机值；eapi 的加密头与 HTTP Cookie 白名单又不包含该字段。实际浏览器出站 Cookie 则保留了用户提供的值。两边 `MUSIC_U`、`__csrf` 相同，不代表完整请求身份相同。

上游 [PR #243](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/pull/243) 的三个修复分别处理了[服务器值采集](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/commit/5c98a9a1eaf30a219d2c779bd4668609bc17405d)、[调用方值优先](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/commit/8376699f5e187e5d5324b7e73bc387ec941b075c)、[eapi 实际发送遗漏](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/commit/22003c2c322387aba696232abf74a0163aebf723)，没有提供收藏 405 恢复证据。更早的 [Binaryify #1788](https://github.com/Binaryify/NeteaseCloudMusicApi/issues/1788) 确有取消随机 NMTID 后验证码登录恢复的报告和维护者确认，但那是登录路径。本票仅补入已有 NMTID 的实验仍然 405，不能直接把上游修正当成本票的答案。

### 设备状态、Watchman 状态和固定标记不是同一种东西

[官方设备脚本](https://st.music.163.com/device/signature/create/deviceid.js) 调用 `createNEFingerprint().getToken()`，再请求 `/api/middle/device-info/web/get`。本次从 Chrome 的 `responseReceivedExtraInfo` 中确认实际 `/weapi/middle/device-info/web/get` 响应通过 Set-Cookie 下发 `sDeviceId`，再从后续 `requestWillBeSentExtraInfo` 确认它确实被发送。

[官方 Watchman SDK](https://acstatic-dun.126.net/2.7.5_af2952a4/watchman.min.js) 自己读写 `WM_TID`、`WM_NI`、`WM_NIKE`；其存储处理器从响应取得状态，`WM_NIKE` 的计算涉及 `WM_NI`。所查脚本没有 NMTID、sDeviceId 的直接推导关系，不能把这些字段混称为一个 token。

[官方 injector](https://st.music.163.com/cmf-injector-sdk/injectorsdk.min.js) 对命中域名的 XHR／fetch 写入固定 `Nm-GCore-Status: 1`，并没有在这条路径上计算请求签名。[官方网页 core](https://s3.music.126.net/web/s/core_c7686f506f6f2607bb7f6cea1951f039.js?c7686f506f6f2607bb7f6cea1951f039) 的收藏 handler 只提交 `id`，协议层补充 CSRF 并加密。16:50 的成功收藏实际携带 `sDeviceId`、三个 WM Cookie 和该固定头，但没有观察到 `X-antiCheatToken`。

**共现不等于必要。**16:56 的 SDK 探针只使用用户原始 Cookie，没有浏览器新取得的 `sDeviceId`、WM Cookie，也成功过。因此现有证据不支持要求调用方补齐所有这些字段，更不支持生成静态假 token。

### 默认伪装 IP 的名称与实际网段不符

[`generateRandomChineseIP`](https://github.com/nonhana/hana-music-api/blob/c832da277cdfce9bcf0a4876f01d5f3be1aabe5b/src/core/utils.ts#L15) 的前缀表并非全部来自中国网络。本次保存的**随机伪装值，不是用户实际出口 IP**，在 APNIC RDAP 中分别对应：

| 探针                | 随机地址                                                 | 登记国家／网络       |
| ------------------- | -------------------------------------------------------- | -------------------- |
| 16:56 成功 SDK 探针 | [116.90.50.192](https://rdap.apnic.net/ip/116.90.50.192) | AU／DIGITALPACIFIC   |
| 17:04 失败公开模块  | [116.88.29.192](https://rdap.apnic.net/ip/116.88.29.192) | SG／SGCABLEVISION-SG |
| 16:48 NMTID 探针    | [116.83.56.139](https://rdap.apnic.net/ip/116.83.56.139) | GB／UK-COLT-20070514 |

RIR 登记国家不是网易云采用的地理定位或风控结论，成功样本也并非中国登记地址。对使用 `os=web` 的失败请求仅去掉转发 IP 头仍然 405。因此这里确认了默认 IP 生成器的问题，**没有确认它是本票根因**，本 PR 不顺带修改全局 IP 策略。

## 哪些结论有证据，哪些还没有

1. **Bun 本身不是充分致因。**官方完整请求在 Bun 中成功过；不能把故障归结为“必须从浏览器发送”。
2. **`os=iphone` 是已验证的拒绝条件之一。**同正文、Cookie、头和运行时，只追加这个字段就从 200 变为 405，去掉又恢复。它解释了固定平台身份为什么不能凭一次成功就宣称正确，但不证明所有 iPhone／eapi 请求都会失败。
3. **固定字段方案仍不足以解释所有结果。**16:56 的 SDK 成功探针与候选 B 的失败请求，其 URL、UA、Cookie 名集合及固定值一致；剩余差异包括随机 IP、`NMTID`、`_ntes_nnid`、`_ntes_nuid`、`WNMCID`、`deviceId` 和加密随机数。尚未逐个验证这些差异的因果关系。
4. **成功请求后来也失败，限制了纯静态归因。**17:09 使用的是重放请求，未再发起新的官方界面收藏。可能涉及上游状态变化、请求重放时效或其他上下文；不能据此声称账号已被全局封禁、官方新请求也必然失败，或等待某个固定时间必定恢复。

## 候选与稳定性窗口

候选 A 先修改契约测试，观察到旧实现 4 个相关断言失败；改为网页 UA／weapi／web 标记后，58 个专项测试和类型检查通过。17:02 开始正式窗口：计划 A／B／A 三轮，目标为 `2889745179` 和 `106697785`，都已确认属于他人且未收藏；轮间至少 60 秒，上限 6 个正常写请求／24 个总请求，失败停止。

该窗口第 1 轮收藏失败，**实际 6 个请求、1 个写入尝试、完成 0/3**，后两轮未执行。源码基线 `c832da2` 加候选 A，模块 SHA-256 为 `1aae10c8a45ecabe66e9afa86a8b4037ad97d9038426a87a5827d323f5f80b3b`；本机保留与该 hash 相符的源码快照。

候选 B 只保留此前成功探针对应的 weapi／web 标记变化，仍保留原 iPhone UA、appver、osver、channel；专项测试 8 项和类型检查通过，但公开模块一对验证在收藏阶段再次失败。它是诊断组，**没有作为新窗口替换前一个失败窗口**。

两份候选均未通过真实验证，生产改动与候选测试已撤回，只在本机归档。当前 PR 保持调查草稿。尚无通过的首窗，因此没有可按“首窗完成后至少 24 小时”安排的第二个成功窗口。

下一轮首先需要在新的受控时段取得**新生成的官方成功请求**，再确认其原样 Bun 重放仍成功，建立同时段的成功控制。若控制失败，停止账号写入并记录状态，不能继续比较固定字段。只有成功控制存在，才逐项隔离随机身份差异；不能继续把不同失败路径混成“都是频率限制”。
