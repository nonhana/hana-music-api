# 收藏/取消收藏歌单

> 调用此接口，传入类型和歌单 id 可收藏歌单或者取消收藏歌单

## 接口信息

| 项目     | 值                    |
| -------- | --------------------- |
| 接口地址 | `/playlist/subscribe` |
| 请求方式 | `GET` / `POST`        |
| 需要登录 | 是                    |
| 对应模块 | `playlist_subscribe`  |
| 文档分类 | 歌单                  |

## 请求参数

| 参数 | 类型   | 必填 | 默认值 | 说明                            |
| ---- | ------ | :--: | ------ | ------------------------------- |
| `t`  | string |  ✅  | -      | 类型，1：收藏，其他值：取消收藏 |
| `id` | string |  ✅  | -      | 歌单 id                         |

## HTTP 示例

```bash
GET /playlist/subscribe?t=1&id=106697785
GET /playlist/subscribe?t=2&id=106697785
```

## 编程式调用

```ts
import { playlistSubscribe } from 'hana-music-api';

const result = await playlistSubscribe({
  t: '1',
  id: '106697785',
});

console.log(result.body);
```

## 补充说明

说明 : 调用此接口，传入类型和歌单 id 可收藏歌单或者取消收藏歌单

请求固定以 iPhone 客户端的身份发出：设备信息（`os`、`appver`、`osver`、`channel`）和 User-Agent 都用 SDK 内置的 iPhone 配置，调用方传入的 `os`、`ua` 对这个接口不起作用。业务请求体只带歌单 `id`。

2026-10-17 14:49（北京时间）本机真账号验证：公开 SDK 的 `client.playlistSubscribe` 收藏、取消收藏各成功一次，均返回 `{ code: 200 }`。关闭缓存读取歌单列表，确认目标出现后又消失，收藏数为 35 → 36 → 35，账号歌单列表恢复原状。

::: warning 重复性验证未通过
同日 15:35 追加低频冒烟，计划 3 轮、轮间隔 60 秒，每轮收藏后立即取消，并读列表确认状态。使用同一账号、同一目标、相同 iPhone 请求配置，关闭缓存与重试；首轮收藏就返回 HTTP 200、`code: 405`“操作过于频繁，请稍后再试”，随后停止，未执行后续轮次。列表确认账号状态未改变。这说明当前写法有成功记录，但不能视为稳定的解决方案；本次距离此前成功约 45 分钟，仍不足以区分账号风控、请求身份或其他上游原因，恢复条件尚未确定。
:::

此前 14:50 的补充验证中，收藏自己的临时歌单返回 HTTP 200、`{ code: 401, message: '歌单创建者已设置隐私' }`，SDK 以 `status: 401` 拒绝，正文保持不变。临时歌单创建时使用默认 `privacy=0`，验证后已删除；这是该账号本次实测的返回，不能据此推断所有自建歌单都会返回相同说明。

PC 对照使用 eapi、官方 Mac 3.1.13 的 User-Agent 模板、`os=pc`、`appver=3.1.13`，业务请求体也只有 `id`，仍返回 `code: 405`。失败后停止，没有重试或继续测试 PC 取消收藏。这只说明该组合本次未通过；官方 Mac 客户端实际使用的 `os` 尚未确认，因此暂时保留有成功记录的 iPhone 身份。

同日 16:07–16:13 的后续调查中，官方网页使用同一会话在本机成功收藏、取消；恢复列表后，公开 SDK 仍返回 405。仅将 SDK 改用 weapi，或对冻结的失败请求移除转发 IP 头，也都返回 405。根因尚未确定，不能据此建议调用方切换协议或反复重试。稳定性问题由 [#77](https://github.com/nonhana/hana-music-api/issues/77) 跟进，完整对照及证据边界见[调查记录](../../guide/playlist-subscription-investigation.md)。至少两个相隔 24 小时的真实验证窗口仍未完成。

16:43–17:09 的[深入调查](../../guide/playlist-subscription-research.md)确认：一条官方成功请求在 Bun 中原样发送也成功；只增加 `os=iphone` 就返回 405，去掉后再次成功。但 `weapi + os=web` 的 SDK 候选随后仍失败，且已成功的官方请求重放后来也返回 405。候选正式验证窗口完成 0/3 后停止，代码已撤回。因此既不能把 405 一概解释为频率限制，也不能把更换 `os` 视为已经验证稳定的修复。

17:50 的新官方界面请求也返回 405，但与旧成功请求相比，响应报告的来源地址由 IPv4 变成 IPv6，浏览器状态也有变化。后续网络对照未能固定到预期出口，失败后已停止；这不能证明 IPv6 是根因，也不能把切换地址族或继续更换 Cookie 当作已验证的解决方法。完整结果见深入调查中的[出口对照](../../guide/playlist-subscription-research.md#新官方请求与出口对照)。

网易云拒绝时，SDK 保留业务返回码和说明，不将其他错误改写成“操作过于频繁”。遇到 `405` 等限流返回时会补充 `retryAfter`（上游未给出时默认 30 秒），供调用方安排稍后重试，不代表网易云保证在该时间后恢复。
